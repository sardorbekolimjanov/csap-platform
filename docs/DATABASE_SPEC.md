# CSAP — Database Specification

## 1. Purpose

This document defines the database architecture for the **CSAP — Computer System Anomaly Prediction Platform**.

Primary database technology:

* PostgreSQL
* TimescaleDB extension
* SQLAlchemy
* Alembic

The database must support:

* computer-system registration;
* metric definitions;
* high-frequency time-series data;
* anomaly results;
* forecasting results;
* ML models;
* experiments;
* fault-injection experiments;
* alerts;
* reports;
* users and roles;
* audit information.

The database schema must support scientific reproducibility and prevent ambiguity between observed data, model outputs, and predictions.

---

# 2. Database Principles

The database must follow these principles:

1. Use UUID identifiers for major entities.
2. Store timestamps in UTC.
3. Use timezone-aware timestamps.
4. Keep raw observations distinguishable from processed data.
5. Never overwrite historical experimental results.
6. Store model and experiment versions.
7. Preserve dataset/preprocessing/model metadata.
8. Use foreign keys for relational integrity.
9. Add indexes based on actual query patterns.
10. Use TimescaleDB for high-volume time-series data.
11. Use migrations for all schema changes.
12. Do not manually modify production schema outside migrations.

# 5. UUID Strategy

Major entities should use UUID primary keys.

Recommended:

```sql
id UUID PRIMARY KEY
```

UUIDs should be generated by the application or database using a controlled strategy.

For externally exposed identifiers, UUIDs reduce dependence on sequential integer IDs.

It contains observed metric values.

Recommended structure:

```text

```

Fields:

| Field      | Type             |
| ---------- | ---------------- |
| timestamp  | TIMESTAMPTZ      |
| system_id  | UUID             |
| metric_id  | UUID             |
| value      | DOUBLE PRECISION |
| quality    | VARCHAR(30)      |
| created_at | TIMESTAMPTZ      |

Recommended quality values:

```text

MISSING

```

Primary logical key:

```text

```

---

# 12. Time-Series Requirements

`metric_samples` must be optimized for queries such as:

```text
Get all metrics for system X
between time A and time B.
```

and:

```text
Get metric Y for system X
between time A and time B.
```

Primary query dimensions:

1. timestamp;
2. system;
3. metric.

Recommended indexes must be validated against actual query plans.

---

# 13. Retention and Compression

Retention policies must not be enabled blindly.

For the research environment, historical data must be preserved sufficiently for:

* experiments;
* reproducibility;
* dissertation results;
* model comparison.

If storage becomes a limitation, retention/compression policies must be explicitly documented and experimentally safe.

# 28. JSONB Usage

JSONB is permitted for genuinely variable configuration data.

Appropriate uses:

```text
model parameters
preprocessing configuration
feature configuration
experiment configuration
fault configuration
environment metadata
```

JSONB must not replace normal relational columns when the data is:

* frequently queried;
* indexed;
* relational;
* required for integrity.

---

# 29. Timestamp Policy

All persisted timestamps must use:

```text
TIMESTAMPTZ
```

All application-level timestamps should be normalized to UTC.

The frontend may convert timestamps to the user's local timezone for presentation.

Database storage must remain UTC-consistent.

---

# 30. Dataset Versioning

A model or experiment must not merely reference a generic dataset name.

At minimum, store:

```text
dataset_version
```

For stronger reproducibility, future versions may include:

```text
dataset_hash
source_uri
collection_period
feature_schema_version
```

Examples:

# 33. Indexing Strategy

Initial indexes should prioritize:

### Metric queries

```text
(system_id, timestamp)
(metric_id, timestamp)
```

### Anomaly queries

```text
(system_id, timestamp)
(model_version_id, timestamp)
(is_anomaly, timestamp)
```

### Forecast queries

```text
(system_id, forecast_start)
(forecast_result_id)
```

### Experiment queries

```text
(experiment_id, created_at)
(status, created_at)
```

Indexes should be validated with actual workload measurements.

# 34. TimescaleDB Strategy

The primary time-series candidate is:

```text
metric_samples
```

Potential future hypertables:

```text
anomaly_results
forecast_values
```

These should only become hypertables if measured data volume and query patterns justify it.

The architecture must avoid introducing TimescaleDB features solely for complexity.

---

# 35. Data Integrity

The database must enforce:

* valid foreign keys;
* non-null required fields;
* unique identifiers;
* valid status values;
* non-negative durations where applicable;
* valid timestamps;
* valid metric relationships.

Application validation must complement database constraints.

---

# 36. Scientific Data Immutability

The following records should be treated as immutable after completion:

```text
metric_samples
completed experiment_runs
experiment_metrics
completed anomaly_results
completed forecast_results
fault_injections
```

Corrections should preferably create a new version or corrected record with an audit trail rather than silently modifying historical research evidence.

---

# 37. Migration Strategy

Alembic must be used for schema evolution.

Rules:

```text
Model change
    ↓
Alembic migration
    ↓
Migration test
    ↓
Application test
    ↓
Commit
```

No production schema modification should bypass migrations.

---

# 38. Seed Data

Development environments may include seed data for:

* roles;
* development user;
* example metric definitions;
* example system.

Seed data must never contain real credentials.

Production initialization must use secure configuration.

---

# 39. Backup Requirements

Research data must be backed up before major schema changes.

At minimum, backup strategy should distinguish:

```text
database backup
ML artifacts
experiment reports
configuration
```

Model artifacts stored outside PostgreSQL must have their own backup/versioning strategy.

---

# 40. Database Security

Required principles:

* database credentials must come from environment/secrets;
* application should use a dedicated database user;
* administrative credentials must not be embedded in source code;
* production database should not be publicly exposed;
* least-privilege access should be used;
* sensitive audit information should be protected.

# 42. Database Definition of Done

The database phase is complete when:

* all core entities are defined;
* relationships are defined;
* UUID strategy is implemented;
* timestamps use UTC-aware types;
* metric samples are optimized for time-series access;
* TimescaleDB integration works;
* Alembic migrations work;
* seed data works in development;
* database constraints are tested;
* repository tests pass;
* no research data is silently overwritten.
